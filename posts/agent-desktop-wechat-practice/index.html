用命令行操作微信：我的 agent-desktop 本地实践

# 智能体# agent-desktop# 桌面自动化# Rust# 微信

摘要：我在 Windows 上拉取并编译了 Vercel Labs 的 agent-desktop，尝试用命令给微信好友发送一条“你好”。过程中遇到了控件不可见、点击返回成功但聊天没有切换，以及输入前焦点丢失等问题，最终通过读取界面、搜索联系人、剪贴板粘贴和快捷键完成发送。本文记录这次尝试，解释它通过系统可访问性接口操作桌面的原理，并讨论如何在外部接入 LLM，实现定时检查新消息和自动回复。

一、从“把项目启动起来”开始

最初看到 agent-desktop 时，我想先把项目拉到本地跑起来，再看看它能不能控制常用软件。我甚至提前准备了模型接口地址、API Key 和模型名称，打算在启动时填进去。

看完项目说明才发现，它的使用形态与我最初预想的不同：agent-desktop 提供 Rust 编写的 CLI 和 C 库，由调用方组织操作步骤。原生命令行工具没有聊天界面，也不内置负责理解任务的 LLM。

因此，这次运行不需要配置模型。编译完成后，每执行一条命令，就启动一个进程、完成一次操作、返回 JSON，然后退出。所谓“启动成功”，在这里表现为命令能运行、系统状态能读取，而不是浏览器打开一个本地页面。

我随后选了一个能检查实际效果的任务：通过命令打开微信中的指定聊天，发送“你好”。操作过程中没有手动点击联系人或输入消息，界面读取和动作执行都由项目命令完成。

文中的联系人统一替换为“测试好友”，省略真实备注和聊天记录；操作流程来自这次实际尝试。

二、项目如何理解和操作桌面

1. 把窗口读取成可访问性树

桌面应用可以通过操作系统的可访问性接口暴露窗口、按钮、文本框、列表等控件。agent-desktop 读取这些信息，将界面表示为树状结构。在 Windows 上，对接的是 UI Automation；项目也分别提供 macOS 和 Linux 的平台适配层。

它能读取到什么，取决于应用暴露了什么。某个控件出现在树里，也不代表它当前可见、可点击或能通过语义接口完成操作，这一点在微信实践里很快就遇到了。

2. 用快照中的引用操作控件

执行 snapshot 后，输出中的控件可能带有这样的引用：

前半部分对应快照，后半部分标识其中的元素。后续 click、set-value、type 等命令可以接收这种引用，定位需要操作的控件。

引用依赖当前快照。界面变化后，应重新读取受影响区域或获取新快照，不能把某次运行生成的引用当成永久控件 ID。在 PowerShell 中还需要给它加引号，否则 @ 可能被解释为 PowerShell 的语法。

3. 默认语义操作，也支持真实输入

默认情况下，工具优先通过可访问性接口调用控件动作，例如调用按钮的操作方法。这类操作可以不移动鼠标，也不抢占前台。

需要切换窗口焦点、模拟键盘或移动鼠标时，可以显式添加 --headed。在本次 Windows 尝试中，最终发送消息依靠的就是前台窗口中的快捷键和粘贴操作。

4. 完成一次操作，还要重新观察

工具返回的 JSON 包含 ok，动作结果中还会包含 disposition。例如，delivered_unverified 表示动作已交付，但效果没有经过验证；它不能直接证明聊天切换成功或消息发送成功。

最后一次读取中，目标聊天输入框已清空，消息列表里出现了“你好”。这是我判断本次发送操作完成的依据；它不表示对方已经阅读消息。

从查找微信进程，到核对发送结果，整个过程没有调用 LLM 接口。负责决定操作顺序的是外部调用方，agent-desktop 负责执行每一步并返回结果。

五、这次尝试暴露出的边界

我原本以为，只要能从界面树拿到按钮和输入框，后面就是固定的一串命令。实际使用后发现，读取到控件、控件可操作、操作产生预期效果，是三个需要分别检查的条件。

实际遇到的情况 本次处理方式
默认深度下看不到搜索框和消息输入框 增大快照读取深度
控件被判定为 offscreen 恢复窗口、检查前台状态，并重新获取快照
点击返回已交付，但聊天没有切换 检查标题后改用搜索路径
模拟输入前控件失去焦点 改用剪贴板和应用快捷键
动作只返回 delivered_unverified 重新读取实际界面确认效果

这些现象来自本次 Windows 微信环境，不能据此断言所有微信版本都一样，也不能把剪贴板方案当成对所有应用通用的解决办法。

对于发送消息这种有外部效果的操作，我尤其不会把“返回值看起来成功”当成唯一依据。若一次发送的结果不确定，先读取消息列表，再决定如何处理；直接重试可能给对方连发两条。

六、后续可以怎样接入 LLM 自动回复

手动组织命令验证了执行链路，下一步可以在外部写一个常驻程序，把新消息观察、模型生成和命令执行连接起来。下面是后续设计，尚未实现或验证。

1. 定时观察，并维护消息处理状态

可以用 Python 或 Node.js 编写后台调度程序，在用户已登录的交互式桌面会话中，定时调用 agent-desktop 获取界面快照，再由程序提取会话和可见消息。

调度器负责周期触发；操作过程中若要等待界面条件，应使用工具提供的等待能力或有截止时间的条件检查，而不是每一步都固定睡眠几秒。

难点在于，桌面快照并不是微信消息订阅接口。当前界面可能只显示一部分会话或消息，未读标记也可能随着打开聊天而变化。因此，真正开始自动回复前，还需要单独验证新消息发现率、会话切换和消息方向识别，不能假设一份快照就包含全部新消息。

2. 把模型接在外部控制程序中

agent-desktop 继续负责桌面执行，外部程序通过模型服务 API 生成回复。模型地址、名称和密钥由后台程序读取环境变量或私有配置，不写进博客、前端构建变量或仓库。

本次使用的 VITE_* 配置没有进入原生命令行工具。后续若编写服务端控制程序，可以自行约定 LLM_BASE_URL、LLM_API_KEY 和 LLM_MODEL，由这一层读取并使用；这些也不是 agent-desktop 自带的配置项。

我会先让模型只生成待发送文本，由程序固定执行经过验证的流程。好友发来的消息应作为待处理内容，不能获得修改目标联系人、读取其他聊天或任意执行命令的权限。

3. 先解决重复回复和会话串线

自动回复程序至少要记录会话标识、已处理的入站消息、回复内容和发送状态。若没有可用的稳定消息 ID，可能需要组合会话、发送方、时间、内容及相邻消息做去重，并接受这种方式仍会存在误差。

尤其不能只用“消息文本是否出现过”去重：同一个人可能连续发两次“你好”，也不能把刚刚由程序发出的内容识别成新的入站消息。

同一时刻只让一个执行任务控制微信，避免两个轮询任务交错切换联系人。模型生成完成后，还要重新核对聊天标题和最新消息，因为生成期间界面或对话可能已经变化。

4. 从有限范围开始验证

我更愿意先选择少量测试联系人，只生成回复草稿，确认新消息识别、去重和会话定位都能工作，再逐步开放自动发送。

后续还可以加入允许回复的联系人名单、工作时段、回复频率限制、连续自动回复次数上限，以及出错后暂停的机制。对发送结果不确定的任务单独记录并核查，避免模型或调度器盲目重试。

目前，我验证到的是“读取界面、定位指定好友、发送一条消息并检查结果”这一段。要把它扩展为长期运行的自动回复程序，接入模型之外，更需要验证消息发现和发送状态管理。
