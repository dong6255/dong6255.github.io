Qwen3-TTS 本地 GPU 实践：从实时播放卡顿到 CUDA Graph 加速

# Qwen3-TTS# 语音合成# CUDA Graph# PyTorch# Web Audio# 性能优化

把 Qwen3-TTS 放到本机 GPU 上运行之后，我遇到的第一个问题是：模型明明已经在使用显卡，生成一段几秒钟的语音，仍然要等待好几秒。

随后把接口改成分块返回，第一段声音确实更早出来了，但播放过程中仍可能出现停顿。原因很直接：如果生成一秒音频需要超过一秒，前端再早开始播放，也迟早会把缓存消耗完。

这次实践最终采用了两条配合使用的改进路线：后端用 CUDA Graph 加速固定长度的音频编码预测，前后端用 PCM 分块传输和 Web Audio 时间轴连续播放。

在这台 RTX 5070 Ti 上，最终一次 1.7B 模型的浏览器测试记录为：首段音频约 0.60 秒返回，2.78 秒生成 4.80 秒音频，实时率约 0.58。这里的首段时间是服务端记录的首块就绪时间，不能直接当作扬声器实际出声延迟。

下面记录排查过程、关键代码、测试结果，以及这套方案仍然存在的边界。

一、选择模型与本地运行环境

Qwen3-TTS 提供预设音色合成、声音设计和声音克隆等能力。这次主要使用 CustomVoice：选择已有音色，输入文字生成语音。

模型 这次实践中的用途
1.7B CustomVoice 默认模型，保留语气指令控制
0.6B CustomVoice 轻量模型，用于速度与资源占用对比，不支持语气指令
VoiceDesign / Base 分别面向声音设计与声音克隆，不属于本文的优化对象

模型能力和接口用法以官方说明为准，不应把一个模型的功能套到另一个模型上。

二、为什么用了 GPU，播放仍然会卡顿

我把问题拆成了三种情况。

1. 等整段生成完，才开始播放

最初的网页使用普通的生成接口：

即使 GPU 推理正常，用户也要等完整流程结束才能听到声音。

还有一个容易误解的参数：non_streaming_mode=False。

在本次使用的官方 Python 封装实现中，这个参数用于模拟流式文本输入，并不会直接把 generate_custom_voice() 变成逐块返回音频的生成器。该方法仍然先等待模型生成，再调用解码器，最后返回完整波形。

因此，不能仅修改这个参数，就认为前端已经拿到了真正的音频流。

2. 提前开始播放，但后续音频供给不足

用实时率 RTF 衡量这个问题更直观：

例如，生成 3.6 秒音频需要 4.7 秒，RTF 约为 1.31。用户可能先听到第一段，但播放器消耗音频的速度高于服务端产生音频的速度，缓存就会逐渐见底。

缓冲只能吸收一定程度的抖动。如果长时间平均 RTF 大于 1，增加缓冲意味着更晚开始播放，并不能让服务端真正追上播放速度。

3. 后端足够快，前端却没有连续调度

另一类卡顿来自播放实现：收到一段就创建一个播放器并立即 play()，或者为每一段单独增加固定等待时间，容易在音频块之间产生空隙。

这种情况下应该检查音频时间轴、排队时长和数据到达间隔，而不是继续缩小模型。

三、先测量，再决定优化哪里

最初两次网页接口复测分别用了约 7.73 秒和 6.70 秒，对应音频时长为 4.40 秒和 3.92 秒。这说明等待确实存在，但还不能直接定位是模型计算、接口、解码还是页面处理造成的。

后续在推理引擎内部分别记录生成、解码和整体耗时，并对完整生成与流式生成分开测试。

CUDA 操作具有异步执行特性。测量 GPU 阶段时，需要在合适的位置同步，否则容易只测到提交计算的时间，而不是计算完成的时间：

这种同步也有开销，适合用于定位和基准测试，不能不加区分地散落在每个小算子之间。

本次观测到，原始内部基准中，生成阶段约 4.75 秒，而完整音频解码只有约 0.04 秒。因此，主要优化对象应当是编码生成路径。

还要注意计时口径：在流式实现里，解码发生在生成过程的回调中，generation_seconds 会包含分块解码花费的时间。不能把它与累计 decode_seconds 再相加，作为整体耗时。

四、先减少固定编码预测的循环开销

在本次版本的模型实现中，每个音频帧有 16 组编码：主生成器负责第一组，内部的 Code Predictor 再生成剩下 15 组。

该内部预测器在当前模型配置中没有 EOS，生成步数是固定的。这让它成为一个比较适合单独优化的部分。

我保留主语音模型原有的生成与结束逻辑，仅把内部的固定步数预测替换为更直接的循环，减少通用生成框架的逐步调度开销。

它也不是任意模型 generate() 的通用替代品。适用前提是当前 Code Predictor 的固定长度、无 EOS，以及已经检查过的输入和输出约定。主生成器仍然需要正常判断语音结束。

线程数也做了对比：这台机器上，四线程稍快于默认线程数；进一步降到一个线程并没有继续提升。固定循环优化后，完整生成从约 4.79 秒降到 4.46 秒，有改善，但不足以解决持续播放时的速度缺口。

五、真正明显的提升来自 CUDA Graph

固定步数只是给下一步创造了条件。

Code Predictor 的常用输入形状固定，步数固定，默认采样参数也固定。如果仍然让 Python 为每个音频帧重复调度同样的 15 步计算，会保留大量重复的主机端开销。

我尝试把这段计算捕获为 CUDA Graph：每次只把新的输入复制到固定缓冲区，再重放已捕获的 GPU 操作。

PyTorch 文档说明了 CUDA Graph 对静态形状、稳定内存地址等条件的要求。因此，这里只捕获符合条件的内部预测器，没有把具有动态文本长度和结束条件的整个 TTS 流程强行放进图里。

有几个细节需要保留：

  • 先预热，再捕获，避免把首次运行的额外行为混进图里。
  • 静态输入和输出需要保持生命周期，不能在每次调用时随意替换底层内存。

  • 形状或采样参数不匹配时，回退普通固定步数预测。
  • 当前代码按单卡、固定精度使用；扩展到多 GPU、其他精度或批量输入时，还要增加设备、精度等检查。

安装前，我用两个测试输入比较原始预测器、固定循环和图重放的贪心输出，并检查连续采样重放是否产生不同结果。它们是防止实现错误的回归检查，不等于已经完成了所有语言、音色与采样分布的完整评估。

这一步之后，1.7B 的一组测试中，生成 4.32 秒音频约需 2.27 秒；流式测试中，生成 4.48 秒音频约需 2.43 秒，首块约 0.54 秒就绪。

六、在生成过程中解码音频，而不是最后切文件

推理提速后，还要让用户尽早拿到可播放的数据。

分块不能只考虑“切多短”

本次默认每 12 个新编码帧输出一块，并为后续解码保留 25 帧左侧上下文：

samples_per_frame 从 get_decode_upsample_rate() 读取，而不是凭模型名字猜帧率。本次解码器配置为 24 kHz、每帧 1920 个采样点，因此 12 帧对应约 0.96 秒音频。

保留上下文是为了减少块边界与完整解码之间的差异，再裁掉已发送部分，避免重复播放。它不保证流式波形与一次性解码逐点完全相同：实测记录中仍有约 0.002–0.003 量级的波形 RMSE。

块太短会增加解码和传输次数；块太长则延后首段返回。12 帧是本次实测采用的折中值，不是适合所有网络和硬件的固定答案。

七、用 NDJSON 传 PCM，前端按音频时间轴播放

服务端采用 HTTP 流式响应，逐行返回 JSON。音频编码为单声道 PCM16 little-endian，再经过 Base64 放入事件中：

选择 PCM 是为了让浏览器直接还原采样点，省去本地流式播放链路中的额外音频格式转码。Base64 会增加约三分之一的数据体积；在 24 kHz 单声道 PCM16 下，原始数据约 48 KB/s，对本机或普通内网场景较容易接受。

连续播放的关键是 nextTime

Web Audio 的 start(when)可以把音频安排到 AudioContext 的时间轴上。这里为每个音频块创建一个 AudioBufferSourceNode，但持续维护同一条播放时间轴：

下一块提前到达时，它会接在上一块的结尾，而不是每块都在上一块结束后额外等待 80 毫秒。只有队列太短或已耗尽时，才用当前时间加少量提前量重新安排。

这 80 毫秒只是本次本地实现采用的调度余量，不是完整的网络自适应抖动缓冲。如果部署到抖动较大的网络，还应增加起播缓冲、记录排队时长和 underrun 次数，并按实际到达情况调整水位。持续播放仍然要求长期供给速度足够快。

另外，实际出声延迟还包含这部分调度余量、音频设备输出延迟等，因此页面显示“首段 0.60 秒”不能表述为声卡已经在 0.60 秒时发声。

八、停止操作需要同时处理前后端

为了让停止按钮真正生效，我保留了两层取消机制：浏览器用 AbortController 结束请求并停止已排入时间轴的音频；服务端观察请求断开，设置线程事件，在后续生成回调中退出。

前端还修正了一个状态问题：调用 source.stop() 同样会触发 onended。如果没有检查本轮编号，旧音频的回调可能把“已停止”覆盖成“播放完成”。上面代码中的 run === generation 就是为了避免这种情况。

后端没有让多个请求同时操作同一个模型。当前实现使用共享锁串行处理生成任务，忙碌时明确返回 429，并以有界队列传递音频块，避免前端处理变慢时无限积压输出。

HTTP 状态码为 200 也不表示整个流已经成功结束。连接建立后发生的错误通过 error 事件返回；只有收到 done，前端才展示本轮完整结果。

九、实测结果与 0.6B 对比

以下是 2026 年 11 月 4 日本机实验留下的记录。内部基准、HTTP 测试和浏览器测试属于不同测量口径，不能把它们当作严格控制所有变量的单一实验。模型启用随机采样，输出时长也会变化。

1.7B 的主要优化阶段

测量阶段 耗时 / 秒 音频时长 / 秒 RTF 首块就绪 / 秒
内部基准：原始预测器 4.79 3.60 1.33 整段返回
内部基准：固定循环、四线程 4.46 3.60 1.24 整段返回
内部基准：流式、未使用图重放 4.70 3.60 1.31 1.29
图重放后的流式基准 2.43 4.48 0.54 0.54
最终浏览器记录 2.78 4.80 0.58 0.60

其中，“最终浏览器记录”的耗时和首块时间是页面展示的服务端统计，不包含扬声器延迟。另一次完整 HTTP 链路测试中，1.7B 首块服务端就绪约 0.86 秒，客户端收到首块约 0.87 秒，也说明结果会有波动。

小模型不一定能消除主要开销

在尚未启用 CUDA Graph 时，0.6B 的内部完整生成测试约为 5.94 秒生成 5.12 秒音频，RTF 约 1.16，仍然没有快于实时。

启用图重放后，一次 0.6B 流式基准约为 2.56 秒生成 4.80 秒音频，RTF 约 0.53，首块约 0.53 秒就绪。它与这次 1.7B 图重放基准的实时率接近。

因此，我没有仅凭参数量就把默认模型换成 0.6B，而是默认保留支持语气要求的 1.7B，把 0.6B 作为可选项。这不是对两个模型音质高低的正式评测，也不代表其他硬件上一定会得到同样结论。

十、验证范围与部署边界

除了“能听到声音”，本次还检查了以下内容：

检查项 实际验证内容
GPU 位置 主模型和解码器参数均位于 CUDA 设备
编码等价性 两个测试输入的贪心输出，与原始内部预测器一致
图重放随机状态 连续采样重放的测试输出有变化
流式长度 拼接后的流式采样数，与最终完整波形采样数一致
分块差异 记录流式拼接与完整解码的波形 RMSE，没有声称逐点相同
取消与恢复 首块前断开、生成中停止后，均能继续发起新请求
界面状态 已停止不会被旧回调覆盖，轻量模型禁用不支持的语气输入
参数与并发 无效参数返回 422，繁忙请求返回 429

这些测试能发现一部分实现错误，但不能代替对多语言、长文本、不同音色和复杂语气的主观试听与质量评估。RTF 小于 1 也只是提供了持续播放的速度余量，网络抖动、系统抢占或浏览器后台节流仍可能造成停顿。

实际接入时，我会继续记录首块时间的 P50/P95、块间到达间隔、播放队列剩余时长与 underrun 次数，而不是只展示一次最好成绩。

Windows 启动阶段还遇到过系统提交内存不足、页面文件错误与权重映射路径的底层崩溃。分片加载和缓冲读取用于绕开本机的加载问题，不是这次推理提速的主要来源，也不能据此断言所有 Windows 或 PyTorch 环境都有相同缺陷。

附件中的缓冲读取器会替换 Transformers 的内部加载入口，仅在本次版本和可信本地权重上使用。环境正常时，可以关闭这一兼容开关，优先使用原生加载路径。升级依赖后，固定预测器、forward hook 和加载兼容层都需要重新做回归验证。
